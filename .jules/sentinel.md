## 2025-10-18 - Avoid Raw String Injections in `re.sub` Replacement Arguments
**Vulnerability:** Passing untrusted or arbitrary raw string values directly as the second argument (`repl`) to `re.sub()` allows regex backreference evaluation (e.g. `\1`, `\g<0>`), causing string corruption or `bad escape` exceptions if the raw string contains backslashes or capture reference syntax.
**Learning:** Python's `re.sub(pattern, repl, string)` parses replacement string syntax in `repl` unless a replacement callable function is passed.
**Prevention:** Always pass a replacement callable (e.g. `lambda _: raw_val`) when performing literal string replacements with `re.sub()` where the replacement value could contain arbitrary text or backslashes.

## 2026-10-19 - Iterative Unquoting Before HTTP Path Validation
**Vulnerability:** Checking raw URL paths for directory traversal sequences (like `..`) before URL unquoting allows attackers to bypass traversal filters using single (`%2e%2e`) or double (`%252e%252e`) percent-encoding.
**Learning:** HTTP servers must decode/unquote URL-encoded path components iteratively until stable prior to evaluating path traversal rules or joining paths.
**Prevention:** Always iteratively `unquote()` HTTP request paths before checking for `..`, `\`, or `\x00`, and enforce `Path.relative_to` checks against the static root directory.

## 2026-10-20 - Synchronize Multi-Provider Credential Patterns Across Detection & Audit Layers
**Vulnerability:** While documented Anthropic credentials (`sk-ant-api03-...`, `sk-ant-admin01-...`) were mathematically matched by the existing generic `sk-[a-zA-Z0-9_\-]{20,}` pattern with identical span and redaction behavior, adding explicit provider-specific recognition (`sk-ant-(?:api|admin)[a-zA-Z0-9_\-]{20,}`) serves as defense-in-depth, explicit format documentation, and regression protection rather than fixing a demonstrated leakage vulnerability.
**Learning:** When multi-provider LLM adapters (e.g. OpenAI and Anthropic) are integrated, making credential formats explicit in regex patterns improves maintainability, domain clarity, and targeted test coverage across prompt inspection (`SensitiveDataDetector`) and audit logging (`TamperEvidentAuditTrail`) without altering baseline redaction behavior.
**Prevention:** Maintain strict pattern parity across detection and audit layers, pair provider-specific token alternatives with comprehensive test suites (covering complete spans, redaction, non-rehydration, and near-misses), and perform empirical differential verification before classifying format updates as vulnerability fixes.

## 2026-11-02 - Suppress BaseHTTPRequestHandler Runtime Version Disclosure in Server Header
**Vulnerability:** Python's standard `http.server.BaseHTTPRequestHandler.version_string()` concatenates `server_version + ' ' + sys_version`, emitting headers like `Server: BaseHTTP/0.6 Python/3.12.13`. This leaks internal server implementation details and exact runtime minor/patch versions to external clients across both successful and error responses.
**Learning:** Setting `sys_version = ""` alone still leaves a trailing space (`"ServerName "`) because `version_string()` unconditionally joins with `' '`. Fully neutralizing runtime banner disclosures requires overriding `version_string(self)` to return the clean generic token directly alongside setting `server_version` and empty `sys_version`.
**Prevention:** In standard-library HTTP servers, always explicitly define `server_version`, set `sys_version = ""`, and override `version_string(self)` to return a constant, non-disclosing identifier.

## 2026-11-03 - Enforce Fail-Closed Validation on Security Revocation Registries
**Vulnerability:** Returning `False` from revocation query functions (such as `is_revoked(None) -> False`) when passed malformed, empty, or non-string identifiers creates an authorization-friendly answer where callers interpret `False` as "approval is valid and unrevoked", converting invalid input into an authorization pass.
**Learning:** For security-sensitive revocation registries, invalid, missing, or malformed identifiers must never be converted into evidence that an authorization token is safe to use.
**Prevention:** Always fail closed by raising `ValueError` (or equivalent exception) when revocation check methods receive `None`, non-string, or empty/whitespace-only identifiers, ensuring callers cannot mistakenly proceed as if the identifier were unrevoked.

## 2026-11-03 - Reject Empty and Non-Bytes Signing Keys in HMAC Verification
**Vulnerability:** Checking `if signing_key:` instead of `if signing_key is not None:` caused empty bytes `b""` to evaluate as falsy, silently falling back to unauthenticated plain SHA-256 computation while declaring `signature_algorithm: HMAC-SHA256`. This enabled attackers to forge valid-looking HMAC receipts using plain SHA-256 without knowing any secret key whenever verification was executed with an empty key. Additionally, passing non-bytes keys caused unhandled `TypeError` exceptions instead of failing closed.
**Learning:** In Python cryptographic signing and verification routines, empty byte sequences `b""` are truthy falsy and must be explicitly distinguished from `None`. Cryptographic keys must strictly require non-empty bytes/bytearray types and fail closed on invalid inputs.
**Prevention:** Always validate that signing keys are non-empty `bytes` or `bytearray` when supplied, explicitly test falsy key inputs (`b""`, `bytearray()`), and never allow truthiness checks to control fallback between keyed HMAC and unauthenticated hash algorithms.

## 2026-11-03 - Enforce Secret and Signature Format Validation in Authorization Records
**Vulnerability:** In `HumanApprovalRecord` and `TrustedTaskContract`, `sign(signing_secret)` and `verify_signature(signing_secret)` passed raw `signing_secret` directly to `hmac.new()` without type or length checks. Passing an empty key `b""` allowed valid HMAC signatures to be minted and verified with an empty secret, undermining authentication. Furthermore, passing `None` or non-bytes keys raised unhandled `TypeError` exceptions instead of failing closed, and malformed non-hex or truncated signature strings were not rejected upfront.
**Learning:** Cryptographic verification routines in security authorization records must strictly validate both the key material (`isinstance(signing_secret, (bytes, bytearray))` and non-empty) and the signature representation (64-character valid hexadecimal string) upfront before evaluating cryptographic equivalence.
**Prevention:** In all signing and verification routines, validate that keys are non-empty `bytes` or `bytearray`, ensure `verify_signature` fails closed by returning `False` on any malformed key or signature format, and enforce constant-time digest comparison with lowercase normalization.

## 2026-11-03 - Normalize Secrets and Fail Closed on Approval Verification in Action Policy
**Vulnerability:** In `SideEffectPolicyEngine`, `signing_secret` was assumed to be a string and encoded directly via `.encode("utf-8")`, crashing with `AttributeError` if `bytes` or `bytearray` were passed (or `UnicodeEncodeError` on unencodable surrogate strings), and empty strings or empty byte secrets were not rejected, risking empty-secret HMAC minting. Additionally, `verify_approval_record` evaluated `record.expires_at` and `current_time` by converting large integers to float (`float(v)` or `math.isfinite(v)`), which raises `OverflowError` on arbitrarily large Python integers (e.g. `10**10000`).
**Learning:** In Python, arbitrarily large integers cannot be converted to floats or passed to `math.isfinite()` without raising `OverflowError: int too large to convert to float`. Security boundaries that accept integers must bound them using `.bit_length()` or numeric ranges prior to float conversions, and compare integers directly.
**Prevention:** Always check `isinstance(v, int)` separately from `float`, guard against oversized integers using `v.bit_length() > 64`, validate floats with `math.isfinite()`, and compare numeric timestamps directly without lossy float conversion.

## 2026-11-03 - Enforce Fail-Closed Validation for HMAC Keys in Audit and Provenance Chains
**Vulnerability:** In `TamperEvidentAuditTrail` and `LocalProvenanceStore`, HMAC key handling relied on truthiness checks (`if self.hmac_key:`). Passing an empty key (`b""` or `bytearray()`) caused the logger to silently fall back to unkeyed SHA-256 while callers intended keyed HMAC-SHA256 tamper-evident hash chaining. Furthermore, passing invalid key types (such as strings or ints) was not validated upfront at initialization.
**Learning:** In Python cryptographic chains, empty byte sequences evaluate to `False` in boolean contexts. When an optional `hmac_key` is supplied, callers expect HMAC tamper evidence; an empty key should fail closed rather than quietly disabling HMAC and falling back to unauthenticated hashing.
**Prevention:** Always explicitly test `if hmac_key is not None:`, require non-empty `bytes` or `bytearray` (raising `TypeError` on invalid types and `ValueError` on empty keys) at class initialization, and use explicit `is not None` checks across all internal hash calculation routines.

## 2026-11-04 - Validate Capability Signing Secret Types and Reject Falsy Keys
**Vulnerability:** In `CapabilityRegistry.__init__`, `signing_secret` accepted arbitrary types without type inspection (causing deferred `TypeError` exceptions during downstream `sign_capability`), and relied on boolean truthiness (`signing_secret or hashlib.sha256(...)`), causing empty byte secrets (`b""`) to silently fall back to random ephemeral keys. Furthermore, there was no centralized mechanism to load capability signing secrets from the environment (`EPISTEMICOS_CAP_SECRET`).
**Learning:** Cryptographic key inputs must be explicitly validated upfront at component initialization rather than during runtime signing operations. Falsy checks (`secret or fallback`) silently mask misconfigurations when empty byte sequences are provided.
**Prevention:** Always inspect `isinstance(signing_secret, (bytes, bytearray))` upfront, reject empty keys with `ValueError`, defensively cast mutable `bytearray` to immutable `bytes`, and allow resolution from trusted environment variables (`EPISTEMICOS_CAP_SECRET`).

## 2026-11-05 - Enforce Fail-Closed Validation for Authority Signing Secrets
**Vulnerability:** In `AuthorizationAuthority.__init__`, `approval_signing_secret` and `contract_signing_secret` resolution relied on boolean truthiness (`if approval_signing_secret:`, `elif env_approval_sec:`). Passing empty byte sequences (`b""` or `bytearray()`) or configuring empty string environment variables (`EPISTEMICOS_APPROVAL_SECRET=""`) bypassed validation and silently fell back to generating random ephemeral keys instead of raising errors. Additionally, non-bytes types (e.g. integers or strings) were assigned directly without validation, causing deferred runtime errors during cryptographic operations.
**Learning:** Authority-level signing secrets protect critical control-plane boundaries (human approval verification and trusted task contracts). Falsy checks on secrets mask misconfigurations, and mutable bytearrays can be modified externally after authority initialization.
**Prevention:** Always validate `isinstance(secret, (bytes, bytearray))` upfront, reject empty sequences with `ValueError`, defensively copy mutable `bytearray` into immutable `bytes`, and treat empty environment variables as explicit empty configurations rather than unconfigured fallbacks.

## 2026-11-06 - Enforce Key Type Validation and Reject Empty Master Keys in LocalMappingVault
**Vulnerability:** In `LocalMappingVault.__init__`, `master_key` resolution relied on boolean truthiness (`self.master_key = master_key or secrets.token_bytes(32)`). Passing an empty byte sequence (`b""`) evaluated to falsy, silently falling back to generating a random ephemeral 32-byte key instead of raising an error or respecting deterministic key configuration. Furthermore, non-bytes types (such as strings or integers) were accepted without validation, deferring `TypeError` crashes to subsequent runtime `_get_session_key()` calls during HMAC computation, and passing mutable `bytearray` objects left the internal master key vulnerable to post-initialization mutation, which would silently alter derived session HMAC keys across calls.
**Learning:** In privacy and pseudonymization vaults, master cryptographic keys derive session-isolated HMAC keys. Silent fallbacks mask configuration errors, unvalidated key types create deferred runtime failures, and mutable byte structures violate cryptographic key immutability.
**Prevention:** Always validate `isinstance(master_key, (bytes, bytearray))` upfront at component initialization, reject empty sequences with `ValueError`, and defensively cast mutable byte sequences into immutable `bytes`.

## 2026-11-06 - Enforce Fail-Closed Validation for Trusted Exception Tokens in ShowerCurtainGate
**Vulnerability:** In `ShowerCurtainGate.__init__`, `trusted_exception_token` accepted arbitrary types and values without upfront validation. Under a misconfiguration where the gate is instantiated with an empty string or whitespace-only value (e.g. `"   "`), any caller supplying matching trivial whitespace in execution context (`shower_curtain_exception_token: "   "`) would satisfy `hmac.compare_digest` and receive privacy exception bypass (`EXPLICIT_PRIVACY_EXCEPTION_AUTHORIZED_VIA_TRUSTED_TOKEN`) for non-credential sensitive data (PII). Furthermore, non-string tokens (e.g. bytes, ints) failed silently during evaluation instead of failing closed at gate initialization.
**Learning:** Security gates that permit privacy policy exceptions using shared secret tokens must strictly validate that the token is a non-empty, non-whitespace string at initialization. Trivial or falsy tokens turn an exception gate into an open egress bypass when matching context is supplied.
**Prevention:** Always enforce `isinstance(trusted_exception_token, str)` (raising `TypeError` on invalid types) and `bool(trusted_exception_token.strip())` (raising `ValueError` on empty or whitespace strings) upfront in security gate constructors, and canonicalize by stripping surrounding whitespace.
